### Анализ системы в контексте планирования логирования
Логи с уровнем INFO:

- **Shop API**
  - **Login пользователя** - время операции, id пользователя
  - **Logout пользователя** - время операции, id пользователя
  - **Добавление товара в корзину** - время операции, id пользователя, id товара
  - **Создание заказа** - время операции, id пользователя, id заказа
  - **Загрузка 3D-модели** - время операции, id пользователя, id заказа, id файла с моделью
  - **Создание 3D-модели** - время операции, id пользователя, id заказа, id файла с моделью


- **CRM API**
  - **Login менеджера** - время операции, id менеджера
  - **Logout менеджера** - время операции, id менеджера
  - **Назначение заказу менеджера** - время операции, id менеджера, id заказа
  - **Создание заказа** - время операции, id заказа
  - **Изменение статуса заказа менеджером** - время операции, id менеджера, id заказа


- **MES API**
  - **Login оператора** - время операции, id оператора
  - **Logout оператора** - время операции, id оператора
  - **Начало расчета стоимости заказа** - время операции, id заказа
  - **Завершение расчета стоимости заказа** - время операции, id заказа
  - **Изменение статуса заказа оператором** - время операции, id заказа, id оператора


- **Shop DB**, **MES DB**
  - **Начало выполнения запроса** - время операции, тип запроса
  - **Окончание выполнения запроса** - время операции, тип запроса, время выполнения


- **Message Queue**
  - **Отправка сообщения в очередь** - время операции, id очереди, id сообщения
  - **Доставка сообщения** - время операции, id очереди, id сообщения


- **3d storage files**
  - **Загрузка файла** - время операции, id файла с моделью
  - **Чтение файла** - время операции, id файла с моделью

Другие уровни логирования:
- **WARN** - логи, сообщающие об отклонении поведения системы от планируемого и предупреждающие о потенциальных ошибках или проблемах с доступностью/производительностью
- **ERROR** - все события, которые логируются на уровне INFO и заканчиваются ошибкой исполнения
- **FATAL** - падение, недоступность сервисов
- **DEBUG** - логи используются при отладке системы, включаются только на dev-контуре

Логирование WEB-приложений:
- **Internet Shop, CRM, MES** - логирование событий работы UI уровня WARN, ERROR, FATAL

Дополнительные настройки:
- В каждом логе сохраняем Trace ID при условии, что система трейсинга на данном этапе уже внедрена

### Мотивация
Логи помогают при отладке разных компонентов приложения, а также позволяют собирать и анализировать данные о работе системы. Это помогает обнаружить ошибки. Так же логи - это один из источников информации для мониторинга. Логирование позволяет:
- Уменьшить время на обнаружение причин сбоев
- Уменьшить время восстановления работоспособности системы после сбоев
- Вместе с настроенной системой мониторинга, логирование позволяет обнаруживать и устранять ошибки в работе системы до того как их обнаружат пользователи
- Улучшить качество поддержки клиентов
- Исполнять обязательства по обслуживанию системы, прописанные в SLA

Метрики, на которые повлияет логирование:
- Время на обнаружение причин сбоев (техническая)
- Процент ошибок при исполнении операций внутри сервисов (техническая)
- Процент потерянных заказов (техническая / бизнес)
- Удовлетворенность клиентов (бизнес)

Наиболее важный функционал системы - создание, расчет, оформление, исполнение заказов. При этом надо учесть что на данный момент пользователи большего всего жалуются на потерю заказов, их долгое исполнение, медленную работу MES Dashboard, нестабильную работу MES API. Жалоб на работу интернет-магазина зафиксировано практически не было.

Исходя из этого очередность внедрения систем логирования и трейсинга следующая:
1. MES API - критичная часть системы отвечающая за расчет стоимости заказов и за их производство. Так же это входная точна для клиентов, которые оформляют заказы используя API
2. CRM API - модуль отвечающий за управление всеми заказами в системе. Является звеном цепочки расчета стоимости заказа посредством MES API, в т.ч. для заказов, оформленных через интернет-магазин. Так же отвечает за создание заказов при использовании API
3. Message Queue - критичная часть системы для взаимодействия с MES API
4. Shop API, Shop DB - узкое место системы, т.к. Shop DB является разделяемым ресурсом между Shop API и CRM API

### Предлагаемое решение
Предлагается использовать стек ELK. Его составляющие:
- **Beats** (например Filebeat) - утилиты для доставки данных, агрегируют данные из разных источников таких как Kubernetes, Jenkins, Redis
- **Logstash** - серверный конвейер обработки данных, собирает входные данные и отправляет их в Elasticsearch 
- **Elasticsearch** / **OpenSearch** - документоориентированная распределенная база данных NoSQL  
- **Kibana** - инструмент визуализации документов Elasticsearch

Политика безопасности логов
- Все чувствительные данные (email, пароли, номера кредитных карт, телефонов и т.п.) либо маскируются, либо исключаются из логов
- Доступ к логам предоставляется только пользователям с определенной ролью
- Доступ к логам предоставляется только из корпоративной сети VPN
- Передача данных между Beats -> Logstash -> Elasticsearch -> Kibana осуществляется в шифрованном виде

Политика хранения логов
- Для каждого модуля системы (MES API, CRM API, Message Queue, Shop API, Shop DB) создается отдельный индекс
- Логи хранятся 90 дней для быстрого доступа и поиска
- Логи старше 90 дней архивируются
