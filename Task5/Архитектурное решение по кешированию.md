### Анализ системы в плане кэширования
Имеет смысл закешировать следующие части системы:
- **Список товаров** - Shop API
- **Список заказов** - Shop API, CRM API, MES API
- **Стоимость изготовления изделия** - MES API

### Мотивация
Система "Александрит" испытывает проблемы с производительностью, что приводит к финансовым и репутационным потерям компании.
- Списки с товаров и заказов загружаются долго
- Операторы MES сталкиваются с долгой подгрузкой дашбордов даже при использовании фильтрации и пагинации
- Добавились жалобы со стороны пользователей MES API 
- Новых клиентов не устраивает скорость выполнения заказа

Внедрение системы кеширования позволит решить эти проблемы.

### Предлагаемое решение
Предлагается использовать комбинацию клиентского и серверного кэширований
1. **Клиентское кэширование** - Internet Shop, CRM, MES
   - Кэширование статики (иконки, логотипы, favicon, элементы бренд-бука и т.п.) осуществляется встроенными инструментами браузера
   - Периодически обновляемые файлы (js-bundle, css-файлы) при каждой сборке получают уникальные имена, содержащие name/content hash, что заставляет браузер инвалидировать cache при каждом новом релизе    


2. **Серверное кэширование**
    - **Список товаров** (Shop API), **Список заказов** (Shop API, CRM API, MES API)
      
      Операций чтения предполагается больше, чем операций записи. Однако в данном случае важна консистентность данных. Так же нам надо инвалидировать кэш при изменении статуса заказа или кол-ва товара. Поэтому выбираем паттерн `Write-Through`. При `Write-Through` кэшировании, при чтении данных всегда сначала выполняется поиск в кэше. Если данные найдены в кэше, они сразу возвращаются.

    - **Стоимость изготовления изделия** (MES API)

      Расчет стоимости изделия зависит от кол-ва полигонов в 3d-модели загружаемой в виде файла. Поэтому тут важно понимать - можем ли мы в принципе применить кеширование для этой операции (сможем ли мы как-то формализовать ключ кеша). Если это возможно и менее ресурсоемко чем полный расчет стоимости, в данном случае целесообразно применить паттерн `Cache-Aside`. Расчет для определенного ключа будет производиться один раз, а использоваться (операция чтения) несколькими системами.


3. Почему не подходит `Cache-Aside` для **Списка товаров** и **Списка заказов**
   - Данные не сразу попадают в кеш, поэтому при первом чтении новых данных будет кеш-промах
   - Возможны устаревшие данные в кеше
   - Нужно будет реализовывать инвалидацию кеша при изменении статуса заказа или кол-ва товара

### Стратегия инвалидации кеша
При паттерне кэширования `Write-Through` инвалидация не нужна или, по крайней мере, не является критической. В `Write-Through` все записи сначала пишутся в кэш, а затем параллельно или немедленно сохраняются в основной хранилище (например, БД). Поскольку изменения сразу же синхронизируются, кэш всегда будет актуальным, и инвалидация не требуется для поддержания согласованности данных

Если все же будет принято решение реализовать инвалидацию кеша для Списка товаров/заказов, а так же если возможно реализовать кеширование расчета Стоимости изготовления изделия, в этом случае будет целесообразно применить инвалидацию по ключу при каждом изменении / расчете. Нам не надо инвалидировать весь кеш, т.к. изменилась конкретная запись.
